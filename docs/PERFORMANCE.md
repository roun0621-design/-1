# PER-001 — 다수 동시접속 성능 / 실 운영 근거

> 평가 항목: **"실 운영에서 다수 동시접속 운영 경험 및 성능"**

## 1. 결론 요약

- **실제 대회 운영 이력 보유** — 실업/연맹 주관 전국 규모 대회를 본 시스템으로 실운영. (현재도 국제대회 라이브 운영 중 — §2)
- **단일 인스턴스에서 초당 6,000+ 요청, 2만 요청 무에러** 처리 (읽기/조회 경로, §4 측정).
- 동시성 200까지 **p95 < 100ms**, 에러율 0%.
- 동시접속 대비 아키텍처: PostgreSQL 커넥션 풀, WebSocket 실시간 push, 레이트리밋 보호 (§3).

## 4. 부하 테스트 결과 (재현 가능)

**측정 방법**: 다수 관중/심판이 동시에 대시보드·결과·종목을 조회하는 시나리오를
HTTP 읽기 부하로 재현. keep-alive 연결 재사용(실제 브라우저와 동일). 요청 2만 건/회.
경로: `/api/health`, `/api/competitions`, `/api/events`, `/dashboard.html` 라운드로빈.

**측정 환경(보수적)**: 로컬 단일 인스턴스, SQLite 백엔드, 동일 머신에서 다른 서버도 동시 구동.
→ 운영(PostgreSQL + 전용 인스턴스)은 이보다 동시성·처리량이 더 우수.

| 동시 접속 | 처리량(RPS) | p50 | p95 | p99 | max | 에러율 |
|---:|---:|---:|---:|---:|---:|---:|
| 50  | 6,207 | 7.1ms | 13.0ms | 14.9ms | 132ms | **0%** |
| 100 | 6,616 | 13.4ms | 24.7ms | 26.2ms | 231ms | **0%** |
| 200 | 6,425 | 27.1ms | 50.1ms | 55.5ms | 880ms | **0%** |
| 500 | 6,285 | 50.8ms | 95.3ms | 482.9ms | 3,167ms | **0%** |

- 동시 접속 **200명까지 p95 50ms 이하**, 전 구간 **에러 0건**.
- 동시 500에서도 처리량 유지(6,285 RPS), p95 95ms — 단일 프로세스 한계 구간(p99 상승)이나 무에러.
- 일반 대회의 동시 관중·심판 수를 크게 상회하는 부하에서도 안정.

**재현 명령**
```bash
# 1) 격리 인스턴스 (운영 DB 무관, 레이트리밋 해제)
DB_BACKEND=sqlite SQLITE_PATH=/tmp/lt.db PORT=3100 RATE_LIMIT_MAX=100000000 node server.js
# 2) 부하 측정
BASE=http://localhost:3100 CONCURRENCY=200 TOTAL=20000 node scripts/http_load_test.js
```

**DB 동시쓰기 테스트(PostgreSQL)**: `scripts/load_test.js` — 동시 INSERT의
p50/p95/p99/max latency와 데드락 발생 건수를 측정(기본 동시성 50 / 1만 건). PG 환경에서 실행.

## 5. 평가 답변(요약 문구)

> 본 시스템은 실업/연맹 주관 전국 대회 및 국제대회(2026 코리아오픈)에서 실제 운영되었으며,
> 현재도 라이브 운영 중이다. 부하 테스트 결과 단일 인스턴스 기준 초당 6,000+ 요청을
> 무에러로 처리하고 동시접속 200에서 p95 50ms 이하를 유지한다. 운영 환경은
> PostgreSQL 커넥션 풀·WebSocket 실시간 전송·레이트리밋 보호·무중단 배포(자동 롤백)로
> 다수 동시접속 운영에 대비되어 있다.
